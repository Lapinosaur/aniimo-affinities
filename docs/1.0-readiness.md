# 1.0 readiness

## Implemented for 0.4

- Same-volume atomic executable replacement; exclusive update lock; previous EXE backup.
- Startup acknowledgement after five seconds of UI event processing. Thirty-second timeout rolls back the launched child. This does not guarantee later sessions cannot crash.
- On next launch, interrupted installations use a recovery journal.
- Download cancellation and progress; skipped versions are ignored by automatic checks but remain available manually.
- Stable per-user settings path, including tutorial.txt. Cache cleanup does not reset preferences or remove pending payloads.
- Diagnostics report only version, OS/runtime, display options and last exception type/code/time. No automatic diagnostic upload.
- CI release workflow builds, checks, computes SHA-256 and uploads the exact tested EXE. Existing releases are never overwritten.

## Required manual acceptance (not yet verified)

- Windows 10 x64, standard user, .NET Framework installed, first run and upgrade.
- OBS window/game/display capture and Discord sharing: normal view, overlay, lock/unlock, minimize, Alt+Tab. Document which capture methods work.
- Mixed-DPI monitors, 1366x768, 1080p and 4K; change monitors at 50–150% and verify every action remains reachable.
- Offline startup, cancelled download, restricted folder, antivirus lock, app running twice, reboot during install, crash before acknowledgement.
- External tester feedback on tutorial, key capture/hold, contrast and readable tooltips.

## Rights and signing decisions

The repository README records unresolved redistribution rights for community type artwork. Before broad distribution, obtain suitable authorization or replace it with assets whose rights are established. The original code is now MIT licensed; this does not cover third-party artwork. See THIRD_PARTY_NOTICES.md and docs/signpath-application.md for the review and application draft.

No code-signing certificate is configured. The owner must choose a signing provider/certificate; do not commit private keys. Add signing *before* computing release checksums, using repository/environment secrets and an approval-controlled CI signing step. Signing is not a guarantee that SmartScreen will show no warnings.

## Release procedure

Update package.json, add docs/releases/vVERSION.md, merge the reviewed changes, then run the Publish stable release workflow from main. It generates version attributes for the portable build, runs tests, publishes EXE and checksum, and dispatches the Discord announcement workflow. If only Discord dispatch fails, retry the announcement workflow rather than recreating the release.

Signing preparation and enrollment checklist: [code-signing.md](code-signing.md). Release validation can enforce trusted, timestamped Authenticode signatures with REQUIRE_CODE_SIGNATURE=true once a provider is configured.

## Discord announcement delivery

Stable releases notify only the matching opt-in role: major `1562796495986626620`, minor `1562796606556864692`, patch `1562796669307846716`. Source roles, Member, everyone and here are never allowed. Prereleases are skipped; editing an existing message never pings.

The workflow records delivery intent and then the Discord message ID in an invisible release-note comment. Repeat dispatches reuse that ID and edit the existing card. An interrupted delivery with only a pending marker stops: inspect the channel and recover using the existing `message_id` input. Do not blindly retry or remove a pending marker without verifying whether a message was posted. No automatic network retries are used. The release workflow uses GITHUB_TOKEN and explicitly dispatches the announcement once because that token does not trigger release-event workflows.
